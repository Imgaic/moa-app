# 임시 결정, 가정, 물어볼 것

구현을 이어가면서 생긴 임시 결정과 가정, 디자이너와 백엔드에게 물어볼 것을 여기에 쌓는다.
기획, 디자인, 데이터 스키마는 모두 확정 전이다. 이 문서의 내용은 규칙이 아니라 "지금은 이렇게 해 두었다"는 기록이다.

- 흐름의 기준은 `docs/user-flow.md`다. 이 문서와 어긋나면 날짜가 더 늦은 쪽이 맞다.
- 디자인의 기준은 피그마 `최종UI` 프레임이다.

## 4. 백엔드에게 물어볼 것

- 데이터 스키마. 프론트의 초안은 `docs/user-flow.md` 9장과 `src/api/`의 타입이다(가짜 데이터로 먼저 개발 중)
- 길찾기 API, 실시간 반영 방식, 게스트 인증 방식(모두 미결정)
- 홈 목록 API(`getPlans`): 내가 참여한 약속을 한 번에 주는지, 지난 약속(`past`)을 빼고 주는지, 정렬은 누가 하는지. 지금 프론트는 홈 카드에 `id`, `title`, `status`, `confirmed.startsAt`, `confirmed.place.name`, `members`(id, name, avatarUrl)만 쓴다(`src/api/plans.ts`)
- 시각의 형식과 시간대: `startsAt`을 시간대가 붙은 ISO 문자열로 주는지. 프론트는 기기 시간대로 "오늘", "내일"을 센다
- 약속 만들기 API(`createPlan`): 보내는 값은 `title`, `durationMinutes`, `dateRange`(`"YYYY-MM-DD"` 두 개), `placeMode`, `fixedPlace`다(`src/api/plans.ts`의 `NewPlan`). 돌려받는 값은 만든 약속과 초대 링크 문자열이다. 링크 형식과 만료(Q5)는 게스트 인증과 함께 정해야 한다
- 장소(`Place`)의 모양: 지금 프론트는 `id`, `name`, `address`만 쓴다. 좌표와 장소 검색 API(카카오 로컬이 후보)를 서버가 감쌀지 앱이 바로 부를지
- 로그인한 나의 정보(`getMe`): 이름과 사진을 어디서 받는지
- 약속 하나 API(`getPlan`): 허브는 `id`, `title`, `status`, `hostId`, `dateRange`, `durationMinutes`, `placeMode`, `fixedPlace`(`id`, `name`, `address`), `members`(id, name, avatarUrl, `submitted`)를 쓴다(`src/api/plans.ts`의 `PlanDetail`). 없는 약속이면 무엇을 돌려주는지(지금은 null), 내가 멤버가 아닌 약속을 열면 어떻게 되는지
- "나"와 호스트 판별: 프론트는 `getMe().id === plan.hostId`로 호스트 화면을 고른다. 게스트(익명) 사용자도 같은 모양의 id를 받는지, 아니면 `getPlan`이 `isHost`나 `myMemberId`를 같이 주는지
- 제안 API(`getProposals`, `proposePlace`): 제안은 `{ id, memberId, place }`, 제안한 순서로 준다고 가정했다. 같은 사람이 같은 장소를 두 번 제안하면 막는지, 정해진 장소 약속과 확정 뒤에 제안을 막는지(서버에서 확인하길 기대한다)
- 마감 API(`closeAndRecommend`): 호스트가 아니면 거절하는지, 마감 뒤 추천 계산이 끝날 때까지 상태가 무엇인지(바로 `recommended`인지, 계산 중 상태가 따로 있는지)
- 초대 링크(`getInviteLink`): 약속마다 고정인지, 부를 때마다 새로 만드는지. 참가자도 같은 링크를 받는지
- 허브를 얼마나 자주 새로 고칠지(실시간 반영 방식): 지금은 화면에 들어올 때와 내 동작 뒤에만 다시 부른다
- 내 입력 API(`getMyAvailability`, `submitMyAvailability`, `src/api/availability.ts`): 한 사람의 입력은 묶음 목록이고 묶음은 `{ dates: "YYYY-MM-DD"[], startMinutes, endMinutes, origin: Place, mode: 'transit' | 'car' }`다. `docs/user-flow.md` 9장 초안과 다른 점: 시각을 "10:00" 문자열 대신 자정부터 센 분(600)으로, 이동수단을 사람당 하나 대신 묶음마다 둔다. 보낼 때는 묶음 전체를 한 번에 보내 앞의 것을 바꾼다고 가정했다. 묶음이 0개면 "입력 안 함"인지, 마감 뒤 저장을 거절하는지, 범위 밖 날짜와 종료 ≤ 시작을 서버에서도 막는지
- 내 입력 저장 뒤 허브의 `members[].submitted`를 서버가 바로 바꿔 주는지(지금 가짜 구현은 묶음이 하나 이상이면 true)
- 게스트 인증(참여 화면, feat/join): 익명 로그인을 무엇으로 하는지, 서버가 "같은 사람이 다시 온 것"을 어떻게 알아보는지(웹에서 새로 고치거나 브라우저를 닫았다 열어도 같은 게스트인지). 프론트는 `getSignedInMe()`(없으면 null)와 `signInAsGuest({ name, photoUri })`가 게스트를 돌려준다고 가정했다(`src/api/me.ts`). 게스트도 로그인한 사람과 같은 모양의 멤버 id를 받는지
- 초대 링크의 코드(Q5): 약속 id와 같은지, 따로 만든 코드인지, 만료가 있는지. 링크 경로는 `/join/<코드>`로 가정했다. 프론트는 `getInvitation(code)`가 약속 요약(`id`, `title`, `hostId`, `dateRange`, `durationMinutes`, `placeMode`, `fixedPlace`, `members`의 id·name·avatarUrl)을 주고 없으면 null이라고 가정했다(`src/api/invitations.ts`). 로그인하지 않은 사람에게 멤버 목록을 보여줘도 되는지
- 참여 API(`joinPlan`): 이미 멤버면 그대로 성공하는지, 마감 뒤에도 참여할 수 있는지, 참여하면 바로 허브의 `members`에 들어가는지
- 익명 참여자가 나중에 가입하거나 로그인하면 기록을 계정으로 옮기는지(Q9)
- 게스트 프로필 사진: 어디에 올리는지(지금 가짜 구현은 기기 안 주소를 그대로 쓴다), 크기 제한
- 후보 API(`getCandidates`, `src/api/candidates.ts`): 후보는 `{ id, startsAt, place, source: 'recommended' | 'proposed', proposedBy, attendeeIds, voterIds, avgMinutes, maxMinutes }`로 가정했다. 순서(추천 순위, 그 뒤 제안)를 서버가 정해 주는지. 추천 나옴 전에는 빈 목록인지
- 투표 API(`vote`): 한 사람이 한 후보에만 투표하는지, 다시 부르면 바꾸는지 거절하는지. 투표하면 `voterIds`에 바로 들어가는지
- 투표 마감 API(`closeVote`): 확정 규칙(가장 많은 표, 동률이면 앞 후보)을 서버가 계산하는지. 호스트가 투표하지 않았으면 거절하는지. 확정되면 `getPlan`의 `confirmed`(`startsAt`, `place`)가 바로 채워지는지, 어느 후보로 확정됐는지(후보 id)도 주는지(지금 프론트는 일시와 장소 이름이 같은 후보를 찾는다)
- 확정 완료 화면을 봤다는 기록을 서버가 사람마다 갖는지, 기기에 둘지(지금 가짜는 앱이 켜져 있는 동안만)
- 후보를 고르는 알고리즘과 이동시간(Q3, Q4): 지금 가짜 후보와 이동시간은 고정 값이다
- 로그인(feat/onboarding): 소셜 로그인 뒤 서버가 "처음 가입"과 "이미 가입"을 어떻게 알려 주는지, 약관 동의와 프로필 완료 여부를 함께 주는지. 프론트는 로그인 단계(`AuthStage`: `signedOut`, `guest`, `terms`, `profile`, `member`)를 `getAuthStage()`로 받는다고 가정했다(`src/api/auth.ts`)
- 약관 API(`agreeToTerms`): 동의한 약관 id 목록을 보낸다고 가정했다. 약관 항목과 문구, 버전을 서버가 내려주는지(지금은 `src/constants/terms.ts`에 고정), 선택 약관 동의를 나중에 바꾸는 API
- 프로필 API(`saveProfile`): 이름과 사진을 보낸다. 사진은 게스트 프로필 사진과 같이 어디에 올리는지 미정. 소셜 계정의 이름과 사진을 기본값으로 받아올지
- "최근 로그인"의 기준(`getRecentSignInProvider`): 기기에 저장할지 서버가 줄지
